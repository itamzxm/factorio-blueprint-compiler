# 真机校验：把蓝图送进 Factorio 本体跑一遍

> 静态 lint 只能判"几何与字段"。**"游戏到底认不认这张图"只有游戏自己说了算。**
> 这一页讲 `tools/factorio_build_check.py` 怎么做到这件事、保证了什么、又没保证什么。

## 它回答什么问题

| 档 | 手段 | 回答 |
|---|---|---|
| L1 静态 | `bp_lint`（毫秒级） | 实体重叠 / 越界 / 地下件配对 / 断头带 / 臂的取放侧 / 供电覆盖 |
| L2 落地 | `tools/factorio_build_check.py`（约 2 秒） | 游戏认不认这张蓝图、多少实体真的建出来了、建的时候报什么错 |
| L3 产量 | 同上 + `--run-seconds` | 真跑 N 秒后产出多少、**箱子里实际是什么** |

L2 的边界要说清楚：**落地 ≠ 能用**。一根臂对着空气照样落地通过。
逻辑正确性只有 L1 那一道，产量只有 L3 能回答。

## 机制

    python tools/factorio_build_check.py 蓝图.txt

一次运行做这些事（对应 `tools/probe_rig.py`）：

1. 在**临时目录**里铺一个一次性 mod（`mods/bp-probe/`），把场景脚本写进 `scenarios/probe/control.lua`。
2. 用 `--mod-directory` 指向那个临时目录 → 装了什么 mod 完全不影响结果。
3. 用 `--config` 把 `write-data` 钉在临时目录 → **你本机的存档、mod 列表、日志一个字节都不动**。
4. `--test-scenario` 无头启动，场景里 `import_stack` → `build_blueprint` → 采样 → `finish_test`。
5. 从 `<write-data>/script-output/bp-probe/result.json` 取读数，进程退出即回收临时目录（`--keep` 可留证）。

退出码：`0` 全部能建 / `2` 有蓝图不能建 / `1` 输入解不开或夹具失败。

不想动本机任何东西、又想知道"这张图游戏收不收"，这是最省事的一条路。

## 要装什么

- Factorio（实测 2.1.24；2.0 的蓝图格式一样，但读数别混用）。
- Python 3.10+。**不需要**装 mod，也不需要开游戏界面。
- 游戏路径：默认按各平台常见安装位置找，找不到就设环境变量：

      set FACTORIO_EXE=<安装目录>\bin\x64\factorio.exe

通过 MCP 的 `bp_verify` 调它还要多一个 `lupa`（`pip install lupa`）；
没装时 `bp_verify` 会**干净降级**到只有 lint，并在回包里说清楚"真机档没跑"，不会假装验过。

## 常用参数

| 参数 | 用途 |
|---|---|
| `--text` | 打印人读摘要，而不是一大坨 JSON |
| `--json out.json` | 把完整结果写文件 |
| `--run-seconds 60` | 建完真跑 60 秒并统计产量（配合 `bp_testbench` 的自测版才有意义） |
| `--powered` | 每根电塔各接一台发电机：只测供电覆盖 |
| `--powered-single` | 只给第一根塔接电，模拟玩家实际只拉一条线：**用来抓"电塔没写 wires"** |
| `--keep DIR` | 保留临时目录，便于取证 |
| `--terrain` / `--fluids` / `--feed-item` | 换地表 / 灌流体 / 预先塞料 |

`--powered` 与 `--powered-single` 的差别抓到过真 bug：24 台石炉阵列边缘的塔没写铜线时，
前者 72 个臂全有电，后者 **58/72 个臂没电**。

## 读回包

`jobs[0]` 里几个字段值得先看：

| 字段 | 含义 |
|---|---|
| `usable.built` / `usable.expected` | 落地了多少 / 蓝图里有多少 |
| `statuses` | 每台机器建成后的状态（`working` / `no_power` / `waiting_for_source_items` …） |
| `production.produced` | 跑了 N 秒后产出总数 |
| `production.drained` | **输出箱里实际收到了什么**——先读物品名，再读数字 |
| `production.theoretical` | 理论上限；读不到 `crafting_speed` 时是 `null`，别当 0 |

`drained` 这一列存在的理由：48 台电炉声明产钢板，`produced 366` 看着很漂亮，
`drained` 却是 `{"iron-plate": 361}`——数量对、物品错。这类错不会让任何断言变红。

## 方向档数实测（另一件只能靠真机的事）

`"这台机器能不能转"`在原型数据里查不到（是 C++ 按 type 定的）。
`tools/probe_directions.py` 把 `direction=0..15` 依次写进单块蓝图、建出来、读回，去重个数就是档数：

    python tools/probe_directions.py --out data/direction-probe.json

结果就是仓库里那份 `data/direction-probe.json`（1028 行原型，含不可放置的），
真值表的 `dirs` 字段从它来。**「能转」和「蓝图里写没写 direction」是两件事**，
详见 `doc/蓝图格式与坑.md` 5.4。

## 它不保证什么

- 不保证逻辑对：一根臂对着空气照样落地通过。
- 不保证产物对：`produced` 大不等于产物是你要的那个（看 `drained`）。
- 不保证性能：读数是这台机器、这个版本下的数，换环境要重测。
- 不碰你的存档：整个运行在临时目录里，`--keep` 之外不留痕。
